# Codex final handoff template

## Actual outcome
One paragraph: what the user can now do, what real data was demonstrated and what remains blocked. Do not lead with a test count or 'product complete'.

## Source and changes
- Repository/branch; base SHA; tested application SHA; published SHA if different; source/lock hashes.
- Exact changed application files and the purpose of each coherent change.
- Whether the implementation was pushed, merely committed locally or delivered as a patch. No implied deployment.

## Search result
State source/universe restrictions, actual period, raw rows, unique candidates, duplicates/invalids, and promoted/rejected/deferred/pending counts at each stage. Distinguish candidate discovery from completed wallet reconstruction.

For each inspected finalist: address, report ID, evidence basis, realised P&L and unit, open/unpriced exposure, median hold, t90, eligible population, strict status, source limitations and why selected/excluded. No invented fills or claims of safe copying.

## Performance and cost
Cold acquisition wall time, time to first shortlist, deep-history throughput, cached refilter median/p95/max, runtime/hardware/memory, external requests, per-provider units used/reserved/remaining, charged spend and budget stops. Separate genuine and synthetic/local measurements.

## Validation and evidence
Actual commands and exit statuses; unique backend nodes versus subtests; frontend/browser results; independent reconciliation scope; source removal/restoration; parent/archive invariance; security/quota tests; contract-checker status. List failed, blocked and not-run checks explicitly.

## Next action
One smallest action per genuine blocker, combined into one user request when permission/access is needed. No indefinite 'wait for more data' without a fixed observation plan, current counts and budget. No repeated planning handoff when implementation can continue.
